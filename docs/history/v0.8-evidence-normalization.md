# v0.8 Test Harness and Evidence Normalization

## 1. Objective

v0.8 standardizes the output of technical tests.

```text
Wazuh / Manual / Other Engine
          |
          v
Normalized Evidence Object
          |
          +-- test
          +-- scope
          +-- traceability
          +-- quality
          +-- event taxonomy
          +-- source health
          |
          v
Control Assessment
```

## 2. Why Normalize Evidence

Without normalization:

```text
SCA output != FIM alert != PostgreSQL audit != vulnerability finding
```

With normalization:

```text
EV-* object
```

provides a common contract for:

- CI
- dashboards
- auditors
- assessment engine
- evidence export
- incident review

## 3. Runtime Transport

The preferred lab transport is the Wazuh Server API `/logtest`.

The API returns structured JSON including:

```text
rule
decoder
agent
manager
full_log
location
token/session
```

Correlation fixtures must reuse the same logtest session token.

## 4. Evidence Contract

Every evidence object carries:

```text
identity
source
observed_at
scope
test
result
traceability
event context
quality
minimized payload
review state
```

The payload must be minimized. Raw Personal Data should not be copied into normalized evidence.

## 5. Anti-False-Compliance Gate

A test result alone cannot create a control PASS.

The aggregator uses conservative precedence:

```text
collector degraded/missing -> REVIEW
ERROR or REVIEW test       -> REVIEW
any FAIL                   -> FAIL
all available tests PASS   -> PASS
```

This is an engineering rule, not a legal rule.

## 6. Legal Boundary

Normalized evidence may contain:

```text
legal_requirements:
  - LR-039-01
```

This means:

```text
the evidence supports a control that traces to LR-039-01
```

It does not mean:

```text
LR-039-01 is legally satisfied
```

## 7. Evidence Quality

Quality remains independent from test result.

Example:

```text
result: PASS
quality: Q1
```

should generally not be sufficient for automated control PASS.

Future versions should allow per-control minimum evidence-quality thresholds.

## 8. Usage

### Static structure

```bash
python3 tools/validation/validate_structure.py
python3 implementations/wazuh/tests/scripts/validate_fixtures.py
```

### Wazuh runtime harness

```bash
export WAZUH_API_URL=https://127.0.0.1:55000
export WAZUH_API_USER=...
export WAZUH_API_PASSWORD=...

python3 implementations/wazuh/tests/harness/run_api_logtest.py
```

### Validate normalized evidence

```bash
python3 tools/validation/validate_evidence.py
```

### Aggregate control assessments

```bash
python3 tools/assessment/assess_controls.py
```

## 9. Result Files

Runtime evidence:

```text
implementations/wazuh/tests/results/
  CASE-001.evidence.json
  CASE-002.evidence.json
  SUMMARY.json
```

Assessment:

```text
assessment/results/
  PDP-ACC-002.assessment.json
  PDP-LOG-001.assessment.json
  SUMMARY.json
```

Generated runtime results should generally be excluded from Git except intentionally curated golden fixtures.

## 10. Future Input Engines

The evidence schema is intentionally not Wazuh-only.

Future producers may include:

```text
OpenSCAP
Keycloak
PostgreSQL
cloud audit
IAM review
document review
manual assessment
ticketing / incident system
```

They can all emit the same evidence contract.
