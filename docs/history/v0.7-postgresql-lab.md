# v0.7 Lab Fixtures and PostgreSQL Audit Profile

## 1. Objectives

v0.7 adds repeatable lab inputs and a PostgreSQL 17 + pgAudit profile.

The release remains:

```text
LAB_VALIDATION_REQUIRED
```

Static repository validation is not equivalent to successful Wazuh runtime validation.

## 2. PostgreSQL audit design

The baseline combines:

```text
PostgreSQL native logging
        +
pgAudit
        +
Wazuh log collection
        +
custom pgAudit decoder
        +
PDP PostgreSQL rules
```

### Privacy-aware default

The example configuration uses:

```text
pgaudit.log = write,ddl,role
pgaudit.log_parameter = off
pgaudit.log_statement = off
pgaudit.log_rows = on
```

`READ` is conditional because exhaustive SELECT logging can produce substantial volume and can itself create additional privacy/security exposure.

## 3. Required database events

Initial event classes:

```text
ROLE
  -> privilege/account management

DDL
  -> schema/object integrity changes

WRITE
  -> data modification evidence

READ
  -> access evidence (conditional)

Repeated READ
  -> anomaly candidate
```

The repeated-read rule is a detection heuristic only.

It must never be labelled automatically as:

```text
confirmed exfiltration
confirmed Personal Data breach
```

## 4. Fixtures

Fixtures live under:

```text
implementations/wazuh/tests/fixtures/
```

Expected outcomes:

```text
implementations/wazuh/tests/expected/EXPECTED_RESULTS.yml
```

The fixtures deliberately contain synthetic names and RFC/documentation-safe IP space rather than production Personal Data.

## 5. Static validation

Run:

```bash
python3 tools/validation/validate_structure.py
python3 implementations/wazuh/tests/scripts/validate_fixtures.py
```

These tests check repository structure and fixture contracts.

They do **not** execute Wazuh analysisd.

## 6. Wazuh runtime test

On a Wazuh server:

```bash
bash implementations/wazuh/tests/scripts/run_wazuh_logtest.sh
```

Or interactively:

```bash
/var/ossec/bin/wazuh-logtest -v
```

The custom decoder must first be installed in:

```text
/var/ossec/etc/decoders/
```

and rules in:

```text
/var/ossec/etc/rules/
```

## 7. pgAudit deployment sequence

Recommended lab sequence:

```text
1. Install PostgreSQL 17
2. Install matching pgAudit 17.x
3. Add pgaudit to shared_preload_libraries
4. Restart PostgreSQL
5. CREATE EXTENSION pgaudit
6. Apply reviewed logging configuration
7. Generate synthetic audit events
8. Confirm PostgreSQL log output
9. Confirm Wazuh collection
10. Confirm decoder
11. Confirm PDP custom rules
12. Record observed fields/results
```

## 8. Synthetic SQL lab activity

Use only lab data.

Example:

```sql
CREATE TABLE pdp_lab_employee (
    id bigint primary key,
    pseudonym text
);

INSERT INTO pdp_lab_employee VALUES (1, 'subject-001');

UPDATE pdp_lab_employee
SET pseudonym = 'subject-001-updated'
WHERE id = 1;

SELECT * FROM pdp_lab_employee;

CREATE ROLE pdp_lab_reader;
```

Do not use real Personal Data as test fixtures.

## 9. Promotion criteria

Each PostgreSQL rule/test must record:

```text
PostgreSQL version
pgAudit version
Wazuh manager version
Wazuh agent version
Linux distribution/version
postgresql.conf relevant settings
pgAudit relevant settings
fixture/input
decoded fields
matched rule ID
expected result
observed result
privacy review
reviewer
validation date
```

Only then promote:

```text
LAB_VALIDATION_REQUIRED
        ->
LAB_VALIDATED
```

## 10. Known limitations

- pgAudit logging is best-effort, not transactional proof.
- Turning on READ logging can create substantial telemetry volume.
- Statement and parameter logging may expose Personal Data or secrets.
- The supplied pgAudit decoder is a draft parsing contract and must be verified against actual output from the target PostgreSQL/pgAudit build.
- A high-frequency SELECT detection is only an anomaly candidate.
- Wazuh evidence supports control assessment; it does not establish legal breach status.
